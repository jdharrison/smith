# Smith Delivery Process

## Status

**Normative target process.** Follow the stricter documented authority boundary when runtime/repository enforcement is incomplete. Configured checks, source-limited review and historical passes are not implemented guarantees, hosted CI execution or human approval. Root `VALIDATION.md` records actual source/artifact-bound outcomes, failures, skips and outstanding gates.

## Work record and branch policy

Every change needs bounded intent and impact-appropriate checks. For routine local work, the explicit user request and a brief conversational scope/check note are the approved local work record; no separate file or work ID is required. Consequential work needs objective, owner, acceptance criteria, risk, exclusions and evidence expectations in optional Jira or a reused approved local task/plan. GitHub is optional for local work; when used it owns commits, PRs/checks/reviews, merge/tag/release records.

| Mode | Ordinary branch |
|---|---|
| Jira feature/defect | `feature/<KEY>-<slug>` / `fix/<KEY>-<slug>` |
| Local feature/defect | `feature/<slug>` / `fix/<slug>` |
| Approved emergency | `hotfix/<slug>` or `hotfix/<KEY>-<slug>` |
| Approved release preparation | `release/v<version>` |

Ordinary work starts from remote `main`; no `develop` exists. `feature/autonomy` remains the one-time bootstrap exception. Do not rename/rebase/force-push it merely to conform. Its approved root-promotion implementation does not include commits, push/PR, merge, tag or branch deletion unless separately authorized. Prefer history-preserving normal merge for the bootstrap cutover; retain local/remote branch and checkpoint ancestry unless named deletion is separately approved.

## Proportionate work and documentation

- **Routine local work:** cosmetic styling/copy, small refactors, and bug fixes restoring an established contract without elevated impact. Use request → brief scope/check note → implementation → focused self-check → concise result. No new plan, full role pipeline, independent subagent review, evidence folder or canonical-doc edit by default. Explicit applicable gates still govern; scope/impact, not diff size or the label “bug fix”, determines the track.
- **Consequential work:** new capabilities, changed contracts or safety/compatibility/operational impact use the canonical lifecycle below. `AGENTS.md`'s elevated triggers always require architecture review and relevant tests. Reuse one active record and still-applicable independent analyses for related follow-ups; document deltas, not repeated background.
- **Reading:** retain already-read policy within a task. Revisit changed or newly applicable sections after scope drift or a new task, and recheck approval/revision binding before effects. Do not reload all entry pages, role prompts or historical evidence each turn.
- **Documentation:** edit the authoritative detailed section only when its contract or operator guidance changes; edit summaries only when they would become inaccurate. Restoring documented behavior does not require narrating the fix into canonical policy. Do not duplicate results across plans, READMEs, validation indexes and architecture reports; historical assessments are not per-fix journals. Keep prior evidence; no automatic deletion or accepted-risk decision follows.
- **Evidence/output:** routine work needs changed files, exact checks/results and remaining issues in a short completion message. Retain long logs and consequential source/artifact/approval evidence in the existing work location, linking rather than copying it into prose. Do not generate hash inventories or large reports for cosmetic edits. Role response templates are proportional, not a requirement for boilerplate on every task.

These tracks govern local work only. They do not waive specific required verification, consequential independent assurance, human signoff, exact external-action approval, security boundaries or release/installed acceptance gates. Reclassify when new impact is discovered; never call required missing/failing evidence PASS.

## Canonical lifecycle

For consequential work: bounded intent → independent producer/architect/designer analyses → planner reconciliation/traceability → resolve blockers → scoped local implementation → developer self-check → fresh independent assurance/adversarial review → human signoff → exact approved external action → separately approved merge/release/deploy/completion where required. No earlier stage substitutes for a later gate. Current chat does not implement this general runtime orchestration; this is the consequential-work development method and future product target. Routine work follows the proportionate track above.

## Triangulation protocol

Producer defines scenarios/blocking acceptance; architect evaluates fit/trust/operations/rollback; designer evaluates visibility/recovery/accessibility. Planner retains `REQ/AC → task → expected evidence`, assumptions/owner/expiry, disagreements and resolutions/blockers. No voting away scope/safety/architecture disagreement. Developer implements the reconciled plan, not new authority. Fresh-context assurance receives requirements/base/diff/evidence/policy, not builder private reasoning. Adversarial review attempts reproducible authorization/injection/path/network/secret/replay/concurrency/cancel/recovery violations. Release judge recommends from evidence; only human accepts risk/approves effects. Authoring session/role cannot finally approve its own consequential work.

## Evidence contract

**Storage/publication:** minimize generated evidence. Prefer one concise command/result/failure summary; do not produce repeated snapshots, manifests, source inventories or log bundles by default. `docs/evidence/` is ignored local storage, not a publication target; historical links there require separately retained local records and may not resolve in a fresh checkout. Keep canonical policy and useful plans tracked. Explicit approval naming the files and purpose is required to commit generated evidence. This storage rule does not waive verification, failure preservation or approval gates below.

For routine local work, record the request/scope, changed files and exact checks/results in the conversation; no separate evidence package is required. For consequential work and external effects, record work ID, requirements/risk/exclusions; repo/branch/base/target/diff/interface identity; exact command/scenario, environment, timestamp, exit/result, artifacts/digests; self-check, independent review/adversarial findings/risks; compatibility/rollback; exact approval binding/outcome and external results. Store this once in the active record/artifact location and link it; do not repeat the package in every document. Missing, unverifiable, stale or narrative-only required evidence is failure, not PASS. Preserve intermediate failures, controlled fixture ignores and skips; counts alone do not bind a candidate. Independently retain consequential artifact/evidence digests outside owner-writable checksum packages. Never retain secrets/raw private transcripts or sensitive paths.

## Required gates

Select required checks by impact before execution and bind to a **stable final source snapshot**. Routine work uses the applicable focused subset; the table below describes component/acceptance evidence, not a demand to run every component/package/release gate after every cosmetic edit. Specific relevant gates remain mandatory. Distinguish a scoped check result from whole-component, installed or release acceptance. Report failures from additional checks, but investigate relevance rather than making every test sharing a broad name filter part of the fix. Unrelated failures remain blockers for the failing suite/acceptance claim, not proof that the scoped change regressed; do not silently drop a required gate after it fails or dismiss uncertain impact. Formatting, compiler/runtime errors, failing required tests, unresolved critical warnings and missing required evidence block the relevant acceptance/release.
